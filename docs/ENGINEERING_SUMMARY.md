# Final engineering summary

Per-run summaries generated by the pipeline itself are in
[`sample-runs/`](sample-runs/). This document summarises the assignment as a whole.

## 1. Plan and rationale

**Reading of the assignment.** Two deliverables are entangled: a URL shortener, and an
agentic system that produces engineering outcomes under governance. The stated
differentiator is the orchestration layer, so the plan was to build that as the product
and make the URL shortener its proof: built by the pipeline in three runs, never by hand.

**Sequence followed.**

1. Fixed the control-plane design first: explicit graph, gates that are code, a sandbox
   with journalled changes, approvals bound to content, an audit log as the single source
   of truth. (Details and alternatives: [ARCHITECTURE.md](ARCHITECTURE.md).)
2. Put a provider seam between agents and the model, so the same agents run against a
   live model or a deterministic replay. This is what makes the control plane testable.
3. Built the engine and ran it against the first playbook as early as possible.
4. Wrote the three scenarios so that each forces a different non-linear behaviour:
   retry (greenfield), rollback and targeted rework behind a change-control checkpoint
   (brownfield), clarification and review-driven re-planning (ambiguous).
5. Wrote the engine test-suite against the real graph, then the end-to-end tests,
   then documentation from the evidence the runs produced.

**Decisions that shaped the result** (each with its cost in ARCHITECTURE.md section 6):

- Agents propose; deterministic gates decide. No guardrail depends on a model's judgement.
- Agents never touch the real codebase; promotion is a separate, approved, reversible step.
- High impact is computed from policy and the real baseline, not claimed by an agent.
- Re-planning is invalidation by input fingerprint, so unchanged work is kept and changed
  work is provably redone.
- The default run is offline and deterministic; simulated parts are labelled in every record.

## 4. Risks, trade-offs and validation

| Risk | Mitigation in this design | Residual |
|---|---|---|
| An agent produces wrong or unsafe code | Tests, coverage and traceability gates; policy scan per change and per workspace; nothing promoted without human release approval | Scanners are heuristic; tests are only as good as the agent's tests - a human still reviews the plan and the release |
| An agent exceeds its remit | Path-confined sandbox; declared write scope enforced; reserved and forbidden paths; no API to approve | In-process agents are not containerised |
| A high-impact change slips through | High impact computed from policy and baseline; entry checkpoint before the task runs | Policy covers paths and task kinds only |
| A sign-off is applied to content it never saw | Approvals bound to content hashes; re-raised on change | - |
| Runaway cost or loops | Bounded retries and rework; invocation and wall-clock budgets as safe-stops | No token-level budget |
| Partial or interleaved writes | Atomic staged apply; journal before files; quiescent restructuring; disjoint write sets enforced by a plan gate | Relies on that gate; no file locking across processes |
| Lost or disputed history | Append-only hash-chained log; metrics derived only from it | Tamper-evident, not tamper-proof |
| Concurrent change to the target | Promotion refused if the target differs from the seeded baseline | No merge; re-run required |

Validation performed: both test-suites green (106 and 201); lint clean; `sdlc demo` from a
clean directory; live HTTP smoke test of the built service; resilience drill with a
permanent fault, a tight budget, a safe-stop and a resume; interactive approval path
exercised through the terminal prompt. Not performed: a run against the real model API; a
build of the generated container image.

## 5. Assumptions

- A deterministic, offline default is more useful to a reviewer than a demo that needs
  credentials; live mode is therefore optional rather than the centre of the submission.
- "Human approval" in a prototype can be a named role asserted on the command line;
  identity and separation of duties belong to the platform it would be deployed on.
- One run at a time per target, on one machine.
- Python, FastAPI and SQLite are acceptable choices for the service; the repository seam
  is the answer to "what about a real database".
- For the service itself: unauthenticated behind a trusted gateway, single instance. These
  are recorded as assumptions A1-A2 in the greenfield spec and revisited in the ambiguous one.

## 6. Limitations

The full list is in [TESTING.md](TESTING.md#limitations). The ones a reader should not miss:

1. The live model provider is unit-tested but has never called the real API.
2. Demo content comes from curated playbooks, and demo reviewers are simulated.
3. Roles are asserted, not authenticated; the audit log is tamper-evident, not tamper-proof.
4. Single process, single machine; agents are isolated by a sandbox directory, not a container.
5. Security scanning is a small set of heuristics.

## 7. What I would do next

1. Run live mode against the API with an evaluation set of requirements, measure first-pass
   gate success per stage, and tune prompts against that number.
2. Give the implementer tools (read, search, run tests) inside the sandbox instead of a
   single call per task, keeping the same gates around it.
3. Put real identity behind checkpoints and anchor the audit head hash externally.
4. Run agents and tests in containers; add token and cost budgets.
5. Replace the JSON snapshot with a transactional store to allow several workers and runs.
