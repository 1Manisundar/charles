# Agentic SDLC orchestrator, demonstrated on a URL shortener

This repository contains two things:

1. **`src/agentic_sdlc/`** - an orchestration layer that takes a requirement through
   requirements analysis, design, planning, implementation, testing, security review,
   documentation and release as an explicit dependency graph, with gates, human
   checkpoints, bounded recovery, policy guardrails and a tamper-evident audit trail.
2. **`service/`** - a URL shortener (FastAPI + SQLite, 201 tests, 100% line coverage)
   that was built by running that orchestrator three times: once from nothing
   (greenfield), once to extend it (brownfield), once from a vague request (ambiguous).

`service/` is not hand-edited: a test asserts it is byte-for-byte what the pipeline produces
(all files except `openapi.json` and `docs/API.md`, which are exported from the app and so
vary with the installed FastAPI version).

## Quick start

Requires Python 3.11+ (developed on 3.13).

```bash
python -m venv .venv
.venv\Scripts\activate            # Windows   (macOS/Linux: source .venv/bin/activate)
pip install -e .

sdlc demo                         # all three scenarios, end to end, about 20 seconds
```

`sdlc` only exists inside the virtual environment. If the shell says it is not recognised,
the environment is not activated: activate it, or call it by path without activating -
`.venv\Scripts\sdlc demo` (macOS/Linux: `.venv/bin/sdlc demo`). `python -m agentic_sdlc demo`
is equivalent when run with the environment's Python.

`sdlc demo` writes a fresh service and the full run records to `demo/<timestamp>/`.
Nothing in it is mocked except the model and the human reviewers (see "What is
simulated" below): the generated code is really written to a sandbox, its test-suite
is really executed with pytest, the application is really imported to export its
OpenAPI schema, and promotion really copies files.

With `uv`: `uv venv && uv pip install -e .`, then the same commands.

### Run the service that was built

```bash
cd service
python -m uvicorn urlshortener.main:create_app --factory --port 8000
curl -s -X POST localhost:8000/api/v1/links -H "content-type: application/json" -d "{\"url\": \"https://example.com/long\"}"
```

See [service/README.md](service/README.md) and [service/docs/API.md](service/docs/API.md).

### Run the tests

```bash
python -m pytest                  # orchestrator: 106 tests, ~20 s (includes the three end-to-end scenarios)
cd service && python -m pytest    # generated service: 201 tests, ~3 s
```

## Be the human in the loop

By default a run **pauses** at every checkpoint and waits for a real decision:

```bash
sdlc run --scenario greenfield --target work/service --run-id g1    # exits 3: paused at plan sign-off
sdlc status g1                                                      # shows the review packet
sdlc approve g1 --decision approve --by you --comment "plan ok"
sdlc resume g1                                                      # runs to the release checkpoint, exits 3
sdlc approve g1 --decision approve --by you
sdlc resume g1                                                      # promotes to work/service, exits 0
```

Other decisions: `--decision reject`, or `--decision changes --target architecture --comment "..."`
to send work back upstream (downstream results are invalidated and the plan is rebuilt).
`--approvals interactive` prompts in the terminal instead; `--approvals scripted` replays a
playbook's simulated reviewers, which is what `sdlc demo` uses.

Inspect any run:

```bash
sdlc audit g1 --verify            # hash chain over every event
sdlc lineage g1 release_report    # what an artifact was derived from, and who decided what
sdlc metrics                      # success rate, retry/rollback frequency, MTTR, latency across runs
sdlc graph g1                     # the run's dependency graph as Mermaid
sdlc report g1                    # engineering summary for the run
sdlc stop g1 / sdlc resume g1     # safe-stop and continue
sdlc rollback g1 --by you         # undo the promotion
```

Resilience drill (inject faults, tighten the budget):

```bash
sdlc run --scenario greenfield --target work/drill --approvals scripted \
         --fault documentation:permanent --max-invocations 8      # safe-stops when the budget is spent
sdlc resume latest --approvals scripted --max-invocations 40     # continues; docs fall back to the template agent
```

## What is simulated, and what is not

| Part | Default (`--provider scripted`) | Live (`--provider openrouter` or `anthropic`) |
|---|---|---|
| Requirements, design, plan, code and docs content | Replayed from `playbooks/<scenario>/` | Generated by the model, constrained to the same schemas |
| Orchestration, gates, policy, sandbox, rollback, audit, metrics | Real | Real |
| Codebase analysis, test execution, security scan, OpenAPI export | Real | Real |
| Human decisions | Real (`deferred`, `interactive`) or replayed and labelled "(simulated)" (`scripted`) | same |
| Failures | Seeded faults declared in the playbook, logged as `fault.injected` | Whatever actually fails |

The scripted default exists so the control plane can be evaluated deterministically and
offline. The playbook content (specs, designs, plans, code) was authored with Claude's
help and reviewed; it is the recorded output an agent would produce, replayed.

### Live mode

Two live providers share one contract: schema-constrained JSON in, a pydantic-validated
object out, every failure mapped onto the engine's retry taxonomy.

```powershell
# OpenRouter: any model, including the free ones (default: nvidia/nemotron-3-super-120b-a12b:free)
$env:OPENROUTER_API_KEY = "sk-or-..."
sdlc --runs work/live/runs run --scenario greenfield --provider openrouter --target work/live/service `
     --max-invocations 22 --max-wall-clock 3600
# pick another model with --model <id>

# Anthropic: needs `pip install -e .[llm]`
$env:ANTHROPIC_API_KEY = "sk-ant-..."
sdlc run --provider anthropic --target work/live/service --requirement "Build a URL shortener with ..."
```

The run pauses at each checkpoint exactly as in the scripted mode. Answer a clarification
with `sdlc approve <run> --decision changes --answer "Q1=..."` (answers are applied by
re-running the analyst, so they need `changes`), then `sdlc resume <run>`. Free models
are slow (30 s to 4 min a call) and OpenRouter allows 50 free requests a day, so give
live runs a larger `--max-wall-clock` and a `--max-invocations` that fits the quota;
`resume` accepts both to extend a run that safe-stopped on a budget.

**What live runs have shown.** See [docs/TESTING.md](docs/TESTING.md#live-runs) for the
record. In short: the control plane behaved as designed against a real model, and the
first live runs found and fixed six defects that the scripted runs could not. RESULT_PLACEHOLDER
The Anthropic provider is still tested only against a fake client.

## Repository map

```
src/agentic_sdlc/        the orchestrator
  workflow.py            the SDLC graph: stages, gates, checkpoints, rework edges
  engine.py              scheduler: parallel dispatch, retry/fallback, rework, reset/revalidate, safe-stop
  gates.py               entry/exit gates (deterministic predicates)
  policy.py              security, compliance and change-control rules
  workspace.py           sandbox, journalled changes, per-node rollback, promotion
  approvals.py           human checkpoints and review packets
  audit.py  metrics.py   hash-chained event log; reliability metrics derived from it
  store.py  models.py    durable run state, versioned artifacts, data model
  agents/                role agents (model-backed and deterministic)
  providers/             scripted replay and live Claude behind one interface
  cli.py  report.py      command line; per-run engineering summary
playbooks/               recorded agent outputs for the three scenarios
service/                 the URL shortener the pipeline built (generated; do not edit)
tests/                   orchestrator tests (engine behaviour, foundations, providers, end-to-end)
docs/
  ARCHITECTURE.md        components, orchestration model, control flow, key decisions
  SCENARIOS.md           greenfield, brownfield, ambiguous: decomposition, orchestration, validation
  TESTING.md             testing approach, limitations, trade-offs
  ENGINEERING_SUMMARY.md plan and rationale, artifacts, risks, assumptions, limitations
  sample-runs/           console transcript, audit logs, review packets and summaries of one demo run
```
